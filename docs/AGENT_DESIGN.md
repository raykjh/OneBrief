# OneBrief Agent Design

기준일: 2026-08-05

## 1. 설계 목표

OneBrief는 해커톤용 일회성 시연이 아니라 사용자가 이후에도 계속 사용할 수 있는 장기 문서 제작 시스템으로 설계한다.

핵심 목표는 다음과 같다.

- 한 번의 목표와 내부자료 입력으로 장기 작업을 시작한다.
- 에이전트가 처리할 수 있는 선택은 사용자에게 반복해서 묻지 않는다.
- 내부자료를 모델의 일반 지식과 공개자료보다 우선한다.
- 예산, 상태, 근거와 수정 이력을 항상 추적한다.
- 정보나 예산이 실제로 부족한 경우에만 사용자를 호출한다.
- 크레딧 종료 후에도 낮은 비용으로 반복 사용할 수 있다.

## 2. 기본 원칙

### 에이전트 수가 아니라 책임 분리가 우선이다

역할마다 반드시 별도의 모델 호출을 만들지 않는다. 의미 판단과 생성이 필요한 역할만 Gemini를 사용하고, 계산·상태 전이·권한 확인·재시도 제한은 일반 코드로 처리한다.

### 자유 대화가 아니라 구조화된 전달물을 사용한다

에이전트끼리 끝없이 채팅하지 않는다. 각 단계는 정해진 입력 스키마를 받고 정해진 출력 스키마를 반환한다.

### 작성자와 승인자를 분리한다

결과물을 만든 에이전트는 자신의 결과를 최종 승인하지 못한다.

### 하드 예산이 항상 우선한다

승인된 비용 한도를 넘어서는 모델 호출은 실행하지 않는다. 필요한 경우 범위 축소 또는 추가 승인 상태로 전환한다.

## 3. 역할별 실행 방식

| 역할 | 구현 방식 | 주요 책임 |
|---|---|---|
| 요구사항 분석가 | Gemini | 목표, 필수정보, 선택정보, 산출물과 성공 기준 추출 |
| 기준 관리자 | Gemini + 규칙 코드 | 자료 우선순위, 충돌, 기준 위반과 근거 누락 검사 |
| 제작자 | 결정론적 코드 + 선택적 Gemini | 토큰·비용·시간·수정 횟수 추정과 단계별 예산 배분 |
| 감독 | Gemini | 전체 전략과 기준 안에서의 자율 결정 |
| 조감독 | 결정론적 워크플로 엔진 | 작업 분해 결과 실행, 순서·상태·체크포인트·재시도 관리 |
| 분석가 | Gemini | 내부자료와 허용된 공개자료에서 근거 묶음 생성 |
| 작성자 | Gemini | 중간 산출물과 최종 장문 결과물 생성 |
| 검증자 | Gemini + 규칙 코드 | 목표·근거·기준·형식 충족 판정과 수정 지시 생성 |

제작자와 조감독을 일반 코드 중심으로 만드는 이유는 비용과 상태 전이가 창의적 판단의 대상이 아니기 때문이다.

## 4. 에이전트 유형

명시적 지시가 없는 자율 선택에만 다음 이분형 유형을 적용한다.

- 속도형 / 깊이형
- 창의형 / 준수형
- 자율형 / 보고형
- 확장형 / 집중형

| 역할 | 기본 유형 |
|---|---|
| 요구사항 분석가 | 깊이형·준수형·보고형·확장형 |
| 기준 관리자 | 깊이형·준수형·보고형·집중형 |
| 감독 | 깊이형·창의형·자율형·확장형 |
| 조감독 | 속도형·준수형·자율형·집중형 |
| 분석가 | 깊이형·준수형·자율형·확장형 |
| 작성자 | 깊이형·창의형·자율형·집중형 |
| 검증자 | 깊이형·준수형·보고형·집중형 |

유형은 작업 계약, 내부자료와 사용자 지시보다 낮은 우선순위를 갖는다.

## 5. 핵심 데이터 객체

### WorkContract

- 목표
- 산출물 목록과 형식
- 성공 기준
- 공개자료 검색 허용 여부
- 최대 예산과 시간
- 최대 수정 횟수
- 사용자 호출 조건

### SourceManifest

- 자료 식별자
- 자료 이름과 유형
- 필수 또는 선택 구분
- 우선순위 등급
- 버전과 업로드 시각
- 추출 상태
- 적용 범위

### BudgetEnvelope

- 전체 승인 한도
- 단계별 한도
- 검증·수정 예비비
- 현재 사용량
- 남은 예산
- 예상 완료 비용 범위

### TaskPlan

- 작업 단계
- 담당 역할
- 입력 전달물
- 예상 비용
- 의존 작업
- 완료 조건
- 재시도 한도

### EvidenceBundle

- 근거 내용
- 출처 자료
- 출처 위치
- 적용할 주장 또는 장면
- 신뢰도와 충돌 여부

### DraftArtifact

- 산출물 종류
- 버전
- 본문 또는 파일 위치
- 적용 근거
- 작성 결정 기록

### ReviewVerdict

- PASS, REVISE, NEEDS_INFORMATION, NEEDS_BUDGET 중 하나
- 위반 기준
- 근거
- 수정 지시
- 예상 수정 비용

### DecisionLog

- 결정 주체
- 선택한 내용
- 적용한 기준
- 대안
- 결정 시각

### FinalPackage

- 최종 산출물
- 기준 검수서
- 결과 검증서
- 근거 목록
- 수정 이력
- 비용 보고서
- 체크포인트

## 6. 상태 기계

```text
RECEIVED
  → CLASSIFYING
  → NEEDS_INFORMATION | READY_FOR_ESTIMATE | UNSUPPORTED
  → ESTIMATING
  → AWAITING_APPROVAL
  → RUNNING_ANALYSIS
  → RUNNING_DRAFT
  → RUNNING_REVIEW
  → REVISING | NEEDS_INFORMATION | NEEDS_BUDGET
  → COMPLETE | PARTIAL | FAILED
```

모든 상태 전이는 저장한 뒤 다음 작업을 실행한다. 프로그램이 종료되거나 서버가 재시작돼도 마지막 체크포인트에서 재개할 수 있어야 한다.

## 7. 사용자 호출 정책

### 직접 개입

사용자는 실행 중 작업을 일시 정지하고 목표, 자료, 예산 또는 중간 결과를 변경할 수 있다. 변경 이후에는 영향받는 단계만 무효화하고 전체 작업을 처음부터 다시 하지 않는다.

### 내부정보 부족

다음 경우 `NEEDS_INFORMATION`으로 전환한다.

- 필수 자료가 없음
- 필수 자료끼리 충돌함
- 성공 기준을 결정할 근거가 없음
- 선택에 따라 결과가 근본적으로 달라지지만 위임 기준이 없음

질문은 가능한 한 모아서 한 번에 전달한다.

### 예산 부족

다음 호출로 승인 예산을 넘을 가능성이 있으면 실행하지 않고 `NEEDS_BUDGET`으로 전환한다.

- 필요한 추가 예산
- 남은 작업
- 예산 추가 시 예상 결과
- 범위 축소 대안
- 현재 결과로 종료하는 선택지

## 8. 예산 정책

- 실행 전 최소·권장·상한 비용을 제시한다.
- 승인 예산의 20~25%를 검증과 수정 예비비로 보존한다.
- 초안 생성이 전체 예산을 소비하지 못하도록 단계별 하드 한도를 둔다.
- 기본 수정 루프는 최대 2회로 제한한다.
- 실제 토큰 사용량을 매 호출 후 기록한다.
- 사용량이 예상보다 빠르게 증가하면 다음 호출 전에 다시 계산한다.

### 모델 라우팅

- 분류·형식 검사·간단한 기준 추출: Gemini 3.5 Flash-Lite 이상
- 감독 판단·복합 분석·장문 작성·최종 검증: Gemini 3.5 Flash 이상
- 동일 품질이면 더 저렴한 모델을 선택한다.
- 고비용 모델은 고정 평가셋에서 품질 향상이 확인될 때만 사용한다.

## 9. 자료 및 기억 구조

### 불변 원본

업로드한 원문은 에이전트가 수정하지 않는다. 수정 결과는 별도 버전으로 저장한다.

### 작업 기억

- 현재 작업 계약
- 최근 체크포인트
- 완료 작업과 남은 작업
- 결정 기록
- 사용 비용

### 장기 사용자 선호

사용자가 명시적으로 저장을 허용한 선호만 장기 기억으로 승격한다. 특정 작업에서 한 번 선택한 내용을 영구 선호로 자동 간주하지 않는다.

### 출처 추적

최종 결과의 중요한 판단은 내부자료 또는 허용된 공개자료의 출처와 연결한다.

## 10. 오류와 재시도

- 형식 오류는 동일 단계에서 저비용 형식 수정 1회를 허용한다.
- 기준 위반은 작성자에게 구체적인 위반 항목만 전달한다.
- 동일한 위반이 반복되면 감독이 전략을 변경한다.
- 최대 재시도에 도달하면 PARTIAL 상태와 실패 보고서를 반환한다.
- 모델 호출 실패는 지수 백오프 후 재시도하되 중복 산출물 생성을 방지한다.
- 체크포인트와 작업 ID를 사용해 동일 작업의 중복 실행을 막는다.

## 11. 권장 기술 구조

- Agent framework: Google ADK
- Model access: Google GenAI SDK를 통한 Vertex AI Gemini 3.5 이상
- API와 UI backend: Cloud Run
- 작업 상태·계약·결정·비용: Firestore
- 원문과 최종 파일: Cloud Storage
- 비동기 실행: 초기에는 Cloud Run 작업 큐, 필요 시 Pub/Sub 추가
- 인증정보: Secret Manager 또는 서비스 계정

초기 버전은 Markdown과 JSON 결과를 우선 지원한다. DOCX와 PDF 패키징은 핵심 수정 루프가 안정된 뒤 추가한다.

## 12. 최적화 방법

### 고정 평가셋

공개 가능한 짧은 내부자료와 의도적 오류를 포함한 목표를 준비한다.

- 필수정보 누락 사례
- 필수자료 충돌 사례
- 내부 기준 위반 초안
- 예산 부족 사례
- 정상 완료 사례

### 측정 지표

- 정상 실행 중 사용자 호출 횟수
- 내부 기준 위반 탐지율
- 잘못된 사용자 호출률
- 첫 실행 완료율
- 수정 후 통과율
- 실제 비용 대비 사전 추정 오차
- 근거가 연결된 주요 판단 비율
- 최종 산출물 완성도

### 최적화 순서

1. 상태 전이와 전달 스키마를 고정한다.
2. 개별 에이전트의 정확도를 평가한다.
3. 전체 수정 루프를 짧은 자료로 반복한다.
4. 모델 라우팅으로 비용을 줄인다.
5. 장문 자료와 실제 ARES 공개 샘플로 확장한다.

## 13. 첫 구현 범위

### 포함

- 목표와 내부자료 접수
- 필수·선택 정보 분류
- 작업 계약과 비용 제안
- 실행 승인
- 분석 → 작성 → 기준 검수 → 결과 검증 → 수정 루프
- 정보 부족과 예산 부족 상태
- Markdown 최종 패키지
- 토큰과 비용 기록
- 체크포인트 재개

### 제외

- 외부 이메일·결제·게시 자동화
- 실시간 협업 편집
- 범용 웹 브라우저 자동 조작
- 영상·음악 생성
- 기업용 다중 사용자 권한 체계

## 14. 지속 사용 조건

해커톤 크레딧이 종료되어도 프로그램은 계속 사용할 수 있다. 사용자는 다음 중 하나를 선택한다.

- Gemini API 무료 구간에서 소규모 작업
- 본인 Google Cloud 결제 계정으로 사용량 기반 실행
- 저비용 Flash-Lite 중심 모드
- 완전 모의 실행으로 계획과 예산만 검토

OneBrief의 핵심 자산은 크레딧이 아니라 작업 계약, 에이전트 권한, 상태 기계, 검증 루프와 평가셋이다.
